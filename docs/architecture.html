The big idea

CrowdRoast is a group-buying marketplace for green coffee. A roaster lists a lot with a deadline, buyers commit kilograms before that deadline, and if the lot hits its minimum, every committed buyer pays the per-bag price tier they unlocked together. The buyer's card is saved at commit time and charged later, bag by bag.

Step 1

Group up

Roasters list a lot with a deadline, a minimum, and one or more volume tiers (price per kg drops as bags fill).

Step 2

Commit, don't pay

Buyers redirect to Stripe-hosted setup. We save the card, run an auth probe, then sit on the commit until the campaign deadline.

Step 3

Pay per bag

If the campaign hits its minimum, settlement writes one commitment_bag_charges row per bag. A daily cron worker charges each bag individually.

⚠ Internalize this

Commit time does not charge a card. It saves one via a SetupIntent. Money moves later, asynchronously, per bag, in the daily charge worker cron. If a buyer's card declines, only the failed bags are affected — successful sibling bags still ship. The legacy "charge-at-commit" payment-mode code path still exists for backwards compatibility but no current lot hits it.

Who plays

Four kinds of actor, three of whom hold money on Stripe Connect.

What they do

Browse open campaigns, commit a quantity in kg, attach a card, and (if the campaign hits its minimum) take delivery at their chosen hub.

What they own

One commitments row per (campaign, buyer). Many commitment_bag_charges rows (one per bag) after settlement. RLS scopes everything to buyer_id = auth.uid().

Dashboard surfaces

Needs attention (failed bag charges), Raising (commits still open), In motion (settled & shipping), Closed (picked up / minimum not met). Portfolio strip shows live exposure, landing kg, savings, YTD spend.

Where it lives

/dashboard/buyer/* · components/buyer-commitments/* · bucket-by-lifecycle.ts for the bag-aware derivations.

What they do

List lots with origin, process, tiers, deadline, minimum, bag size. Manage volume tier discounts. Watch their dashboard for fill rate.

What they own

lots, campaigns (a lot can be re-listed), pricing_tiers, plus a Stripe Connect Express account for payouts.

Payout mechanics

Receives one Stripe Transfer per bag after every sibling commitment_bag_charges row for that bag is terminal. Amount = sum of charged buyer-side cents ÷ (1 + platform fee), rounded per row.

Where it lives

/dashboard/seller/* · lib/settle-bag-pricing.ts · lib/bag-transfer-out.ts handles the actual transfers.

What they do

Physical drop point. Receives the shipment, marks bags picked-up as buyers come by. May host their own catalog of seller lots.

What they own

hubs row + Stripe Connect Express account. Each campaign is bound to one hub. Hub-owned shipments tie buyers to physical handoff.

Payout mechanics

Earns 2% of gross (HUB_SHARE_BPS = 200) on every bag that successfully charges. Same per-bag Stripe Transfer cadence as the seller.

Where it lives

/dashboard/hub/* · bag_transfers ledger row carries hub_id NOT NULL so relisted lots can't backfill prior-hub transfers under a new hub.

What it does

Runs the marketplace. Markup, hub onboarding, settlement orchestration, retries, refunds, admin tooling.

Revenue

Gross − seller − hub. Platform applies a 10% markup to the seller price (PLATFORM_FEE_RATE = 0.10) at commit time. After hub takes 2%, the rest stays with the platform.

Operational surface

Three daily crons keep settlement, expiry, and per-bag charges moving. Stripe webhooks update commitment state asynchronously. Auth probe at setup time keeps "bad card surprises" out of settlement.

Where it lives

app/api/payments/* · app/api/cron/process-bag-charges · lib/charge-worker.ts · app/api/stripe/webhook/route.ts.

The lifecycle

Click a stage to see what happens — including how the system handles failure.

1 Commit Save the card
2 Settle Write bag rows
3 Charge PaymentIntent per bag
4 Transfer Pay seller + hub
5 Ship & Pick Up Buyer takes delivery

1 · Commit — save the card

payment_status: pending_setup → setup_complete
  1. Buyer hits POST /api/commitments with lot_id, qty, hub_id.
  2. Server resolves the active tier, reuses or creates a Stripe Customer, inserts the commitment row with payment_status='pending_setup'.
  3. Server mints a Stripe Checkout Session (mode='setup') and returns its URL.
  4. Buyer redirects to Stripe-hosted setup, attaches a card.
  5. Stripe fires two webhooks (order not guaranteed):
    • checkout.session.completed (mode=setup): writes stripe_payment_method_id + stripe_customer_id, flips status to setup_complete, runs an auth probe (tiny auth-and-void via probeCardAuth).
    • setup_intent.succeeded: same writes, defensive idempotent (never clobbers PM with null, per PR #86).
  6. Auth probe OK → payment_error = NULL = settle-time ready signal.
  7. Commitment now sits at setup_complete with card on file. No money has moved.
SignalWhat happenedHow the system handles it
setup_intent.setup_failed Buyer's bank declined the SetupIntent itself. Webhook cancels the commit and the lot trigger drops the quantity from committed_quantity_kg.
checkout.session.expired Buyer abandoned the hosted page. Same cancel-the-commit path. Skips already-confirmed rows.
payment_error set, status still setup_complete AC12 auth probe (tiny auth-and-void) declined. Buyer is emailed via sendCardAuthFailedEmail (stamped idempotently). Charge worker treats this row as not-ready and never charges it.
PM null + no payment_error (regression) setup_intent.succeeded arrived with no payment_method field and clobbered a previously-written PM (pre-PR #86). Fixed: that handler now only writes PM when truthy and stamps payment_error as a defensive fallback. Existing victims were one-shot rescued via DB hard reset.

2 · Settle — write bag rows

campaigns.status: active → settled OR failed

POST /api/payments/settle-deadlines runs at 00:00 UTC, picks up every campaign whose deadline has passed. The decision tree:

for each campaign whose deadline ≤ now AND status='active':
  if (bags filled) < min_bags_to_succeed:
    cancel every pending commit on this campaign
    campaign.status = 'failed'
    send AC10 "campaign didn't make it" email
    # no refunds — no charges happened
  else:
    resolve active tier (settle-bag-pricing.ts)
    drop orphan commits (setup never completed) ← PR #82
    allocate bags across confirmed commits

    for each (commitment, bag_number):
      INSERT commitment_bag_charges (
        amount_cents,            # buyer-side gross (incl. platform fee)
        kg,
        stripe_idempotency_key,  # deterministic
        payment_status = 'awaiting_charge'
      ) ON CONFLICT (commitment_id, bag_number) DO NOTHING

    campaign.status = 'settled', campaign.settled_at = now()
    # >> NO Stripe call here. Charge worker handles money.
  • Settle-deadlines crashes mid-loop → cron is re-entrant by design. UPSERT with ON CONFLICT DO NOTHING means a re-run is a no-op for any campaign that already finished settlement. The next tick continues.
  • Orphan commit (buyer abandoned setup) → PR #82's filter drops these before bag allocation so they can't crash the settlement loop or eat a bag slot.
  • Campaign goes failed → buyer cards were never charged at this point, so no refunds. Old code (before the bag-aware migration) used to charge at commit and had to refund; that branch isn't reachable anymore.

3 · Charge — one PaymentIntent per bag

awaiting_charge → charging → charged | retry_scheduled | payment_failed

GET /api/cron/process-bag-charges runs at 02:00 UTC daily (Hobby tier cap; Pro would run hourly). Picks up to 100 due rows per tick.

for each row WHERE payment_status IN ('awaiting_charge','retry_scheduled','charging')
                  AND (next_attempt_at IS NULL OR next_attempt_at ≤ now):

  1. Claim 5-minute lease (set payment_status='charging' + expiry)
  2. Gate: payment_error set → markPaymentFailed('auth_probe_failed')
  3. Gate: stripe_payment_method_id null → markPaymentFailed('missing_payment_method')
  4. createAndConfirmPaymentIntent(
       off-session,
       idempotency_key = row.stripe_idempotency_key
     )
  5. Stripe succeeded:
       row.payment_status = 'charged'
       transferOutBagIfReady(...)        # see Stage 4
       sendSettlementEmailIfReady(...)   # AC10 email

The AC13 retry ladder (math in lib/charge-worker.ts):

AttemptOutcomeNext attempt atEmail
1Decline (real)now + 12h—
1→2 transition——AC13 "Your card declined" (idempotent via payment_update_email_sent_at stamp)
2Decline (real)+ 48h—
3Decline (real)—Terminal payment_failed
AnyTransient (rate limit, net)+ 1h—

Lease race: if the function dies mid-Stripe-call, the next tick reclaims after the 5-minute lease expires. Stripe's deterministic idempotency key keeps a rare two-worker race safe — both will get the same intent back.

Vercel return code: 207 (Multi-Status) when any row terminated as payment_failed. That's a normal-day signal for monitoring, not an error.

4 · Transfer — pay seller + hub

bag_transfers row inserted, two Stripe Transfers fire

transferOutBagIfReady fires as a fire-and-forget side-effect from inside the charge worker every time a row terminates.

fired from charge-worker after every charged | payment_failed

if any sibling row for (lot, bag_number) is non-terminal:
  return 'not_ready'   # no-op; next worker tick re-evaluates

if bag_transfers row already exists for (lot, bag_number):
  return 'already_transferred'

split = computeSplit(rows whose payment_status === 'charged')
   seller_amount   = sum( round(amount / (1 + PLATFORM_FEE_RATE)) )
   hub_amount      = floor(total × HUB_SHARE_BPS / 10000)
   platform_keeps  = total − seller − hub

if total > 0:
  Stripe Transfer → seller Connect account
  Stripe Transfer → hub Connect account

INSERT bag_transfers (lot_id, hub_id, bag_number, …)
  # hub_id NOT NULL (PR #85 fix). Prefers campaign.hub_id;
  # falls back to commitment.hub_id for legacy rows.
  • Every bag failed → totalChargedCents = 0. Skip Stripe; write a zero-amount marker row anyway so the bag isn't re-evaluated every tick.
  • Seller has no Stripe Connect account → skip with seller_missing_connect_account. The bag stays in transfer-pending state pending operator intervention.
  • Hub hub_id resolution fails → skip with hub_id_unresolved_on_commitment. Pre-PR #85 this would 500 the worker on the NOT NULL constraint.
  • Transfer succeeded but DB insert failed → next worker tick re-evaluates; Stripe transfers have their own idempotency keys, so the retry doesn't double-pay.

5 · Ship & pick up

commitments.picked_up_at set
  1. Seller creates a shipments row with tracking.
  2. Hub marks shipment.status = 'at_hub' on arrival.
  3. Hub marks each buyer's commit as picked_up (sets picked_up_at, optional picked_up_by).
  4. Buyer dashboard moves the group from "In motion" → "Closed".

The bucketing logic lives in bucket-by-lifecycle.ts. Stage progression for a settled campaign: funds_held → in_transit → at_hub → picked_up → done.

  • Shipment lost → operator marks the commitments as needing manual handling. No code path auto-refunds at this layer — the platform decides.
  • Buyer didn't pick up → no automated escalation. Hub workflow.
  • Refund needed → admin endpoint issues partial/full refunds via Stripe; charge_amount_cents on the commit is updated to the net value (because Stripe webhook updates it on refund).

Background jobs

Three crons run in sequence each night. The 1-hour offsets let each step's writes propagate before the next reads them.

00:00
settle-deadlines

Picks up every campaign past its deadline. Writes commitment_bag_charges rows OR cancels the campaign. Doesn't charge cards.

01:00
lot-expiry

Closes out lots whose expiry_date has passed without re-listing.

02:00
process-bag-charges

The charge worker. Picks up due commitment_bag_charges rows and dispatches one off-session PaymentIntent per row.

All three are protected by the same CRON_SECRET bearer / x-cron-secret header. Vercel Hobby caps cron at daily; Pro can drop the charge worker to hourly and tighten the retry ladder timing.

The charge worker, in detail

If you're debugging a payment failure, this is the file: lib/charge-worker.ts. The per-row state machine:

      ┌─ awaiting_charge ──────┐    (first time the cron picks the row up)
      │                        │
      │   ┌─ retry_scheduled ──┤    (decline, next_attempt_at in the future)
      │   │                    │
      ▼   ▼                    ▼
   [ claim lease → charging (5-min window) ]
                  │
                  │ gate checks: payment_error set?  → payment_failed (auth_probe_failed)
                  │              PM/customer null?   → payment_failed (missing_payment_method)
                  │
                  ▼
         createAndConfirmPaymentIntent (off-session, deterministic idempotency_key)
                  │
       ┌──────────┼─────────────┬─────────────┐
       ▼          ▼             ▼             ▼
    succeeded   transient   real-decline   real-decline (attempt 3)
       │          │              │              │
       │      +1h retry    +12h or +48h     payment_failed (terminal)
       ▼
    charged
       │
       ├── transferOutBagIfReady (fires when all (lot, bag) siblings terminal)
       └── sendSettlementEmailIfReady (fires when all this commit's rows terminal)
Idempotency keys

Original key: charge:campaign:CC:commitment:MM:bag:N. After restart-setup (PR #88), rotated to retry:<new_seti_id>:bag:N so Stripe doesn't replay the cached failure.

Why a 207 from this route is normal

The route returns HTTP 207 Multi-Status whenever any row ended as payment_failed on this tick. Not an error — it's how monitoring distinguishes "all-green tick" from "card-decline tick".

The math

PLATFORM_FEE_RATE = 0.10

Buyer-side amount is the seller's tier price × 1.10. To unwind, the seller's share is the buyer cents ÷ 1.10.

seller   = round(buyer / 1.10)
hub      = floor(buyer × 0.02)
platform = buyer − seller − hub

Real splits are computed per row in lib/payments/settlement-logic.js and summed across charged bags for a (lot, bag_number) before the transfers fire.

Card update flow

When a buyer's bag charges fail, they can replace their card and have the failed bags retried automatically. Shipped in PR #88.

Trigger surfaces

1. The "Update payment" button on the Needs Attention card in the buyer dashboard.
2. The AC13 "Your card declined" email's manage URL.
3. The redirect shim at /dashboard/buyer/commitments/[id].

What it does

POST /api/commitments/[id]/restart-setup mints a fresh Stripe Checkout setup session reusing the existing stripe_customer_id, returns the redirect URL. Webhook re-arm flips payment_failed bag rows back to awaiting_charge with a fresh idempotency key.

Sequence
1. Buyer clicks "Update payment" → POST /api/commitments/[id]/restart-setup
2. Route validates: owner check + has at least one payment_failed bag row
3. Route mints new Checkout Session, updates commit → pending_setup
4. Buyer redirects to Stripe, attaches new card
5. Stripe fires both setup-mode webhooks (order not guaranteed)
6. Both handlers call rearmFailedBagCharges(commitmentId, newSetupIntentId):
     - flip payment_failed → awaiting_charge
     - reset attempt_count = 0
     - clear failed_reason, next_attempt_at, stripe_payment_intent_id
     - rotate stripe_idempotency_key → "retry:seti_NEW:bag:N"  ← critical
     - clear payment_update_email_sent_at
   Gated on probe.ok (CS path) and payment_method present (SI path) so a
   declined new card can NOT unlock retries.
7. Next charge worker tick picks up the rows and tries the new card.

Failure-mode map

"I see X, where do I look?" The shortest path from symptom to file.

Cron returned 207 expected
process-bag-charges responded 207 Multi-Status

That's the documented signal for "this tick terminated at least one row as payment_failed". Not a bug. Inspect the JSON body's failed_reasons array for per-row decline codes.

Look in: app/api/cron/process-bag-charges/route.ts:127

No payout
Campaign settled, seller never got paid

Walk the chain: are the commitment_bag_charges rows all terminal? If yes but bag_transfers is empty, check transferOutBagIfReady — it's a fire-and-forget side-effect that may have skipped (missing Connect account, hub_id unresolved, every bag failed).

Look in: lib/bag-transfer-out.ts · grep logs for [charge-worker] transferOutBagIfReady skipped

Display bug
Buyer dashboard shows $0 across portfolio strip

All four portfolio stats now go through bag-aware effective* helpers (PR #87). If a bag-aware lot reads $0, check that the page is including commitment_bag_charges in the data fetch and passing it via bagChargesByCommitmentId.

Look in: components/buyer-commitments/bucket-by-lifecycle.ts · app/dashboard/buyer/commitments/page.tsx

payment_failed
Bag charge ended missing_payment_method

Commit's stripe_payment_method_id is null but status is setup_complete. Pre-PR #86 this could happen via setup_intent.succeeded clobbering a valid PM. The remediation path is the restart-setup flow.

Look in: lib/charge-worker.ts:274 for the gate; app/api/stripe/webhook/route.ts setup-mode handlers for the write semantics.

Display bug
Settled lot shows "In Motion" but no money moved

Was the buyer's card ever charged? Check commitment_bag_charges.payment_status — if every row is payment_failed, the legacy bucket logic used to leave it in In Motion silently. Fixed in PR #87 by reading bag-aware state via effectiveChargeState.

Look in: bucket-by-lifecycle.ts → hasChargeFailed.

Email
Buyer never got AC10 settlement summary

sendSettlementEmailIfReady is gated on every bag row being terminal AND the transfer-out completing. Check commitments.settlement_email_sent_at. If null, check if transfer-out is stuck (see "No payout" above).

Look in: lib/settlement-email-trigger.ts
